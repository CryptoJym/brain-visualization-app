# 02 — Engineering map and contracts

## Application and data ownership
`src/App.jsx` selects the current app; `src/components/CortexCompass.jsx` owns navigation and shared answer state. Follow its actual import graph, not similarly named dormant legacy components. `src/data/assessmentQuestions.mjs` defines history/support prompts; `assessmentTiming.mjs` handles calendar history; `developmentContext.mjs` and `developmentProfile.mjs` define stage and biological-context normalization. `assessmentProfile.mjs` owns the main persisted profile. It currently writes schema 5 under `cortex-compass-profile`, with questionnaire/evidence/development/context/insight versions, normalized answers, personContext, legacyRecord and neurohero. Saving is explicit, one main localStorage write, with bounded serialized size. Unsupported future versions are refused rather than silently coerced.

`src/data/insightQuestions.mjs` is the separate 16-item current reflection: six possible strengths, six frictions and four resources. `src/utils/insightProfile.mjs` normalizes those answers and selects its small named combinations. Do not merge this layer with the 27-item Deep Hero Atlas or treat counts from one as counts for the other. `src/data/neurohero/processes.mjs` defines functional questions and counterexamples; `compositions.mjs` defines 24 named compositions; `evidence.mjs` provides their research reading. `src/utils/neurohero/engine.mjs` is the LIVE selection engine. It does not import the unfinished graph.

`src/components/neurohero/NeuroheroLab.jsx` presents 12 chapters and eligible signatures. `NeuroheroFieldGuide.jsx` owns the two-page hero guide and strengths card; `NeuroheroReportBlocks.jsx` owns the functional ledger and source explanations in the Scientific Report. `NeuroheroPortrait.jsx` owns appearance controls and accepted portrait display. `HeroAtmosphere.jsx` reuses the stored image as decorative atmosphere, with explicit loading/ready/missing state. The print preparation watches both portrait and atmospheric loading states.

## Reports and assets
`src/components/CompassReports.jsx` is the canonical report renderer and print gate. It switches Superhero/Scientific/card, cinematic/paper, and decorative palette. Private history and biological context are separate unchecked-by-default appendices. Present-day observations and support descriptions can still be sensitive even without those appendices; do not call the whole report anonymous. The strengths-only card is intentionally narrower. `CinematicReports.css` adds visual treatment; `CompassReports.css`, `Neurohero.css` and `DevelopmentContext.css` retain underlying layouts. CSS import order in `src/main.jsx` is material. A generic print `background:white!important` previously overrode cinematic covers; regression checks now verify both modes.

`src/components/HeroEditionShowcase.jsx` introduces fictional art on the landing page. `public/reports/xai/Cortex-Compass-xAI-Signal-Cartographer.jpg` is the approved public fictional sample, not a private user's image. `public/reports/editions/index.json` inventories eight fictional PDFs and hashes, plus the Gamma comparison. Those files are release assets, not evidence of personal generation. `public/brand` contains approved SVG/PNG marks, lockups, icon variants and provenance; root favicon/Apple assets and manifest are also part of the release. Do not replace the approved logo or font files casually.

`CortexBrain.jsx`, anatomy catalogs, `regionStudies.mjs`, `questionRegionLinks.mjs`, `ResearchStudies.jsx` and static brain images implement the research browser. The same teaching anatomy is used for everyone. Geometric surface partitions and schematic inner structures are not atlas-registered participant segmentations. `ATTRIBUTION.md` contains the model licensing/credit requirements. Keep attribution in source and outputs.

## Portrait backend
`worker/index.js` routes `/api/portraits/*` to the `PORTRAIT_SERVICE` Durable Object and otherwise serves `ASSETS` with the existing security headers. `wrangler.jsonc` binds private R2 `cortex-compass-private-portraits`, the SQLite Durable Object class `PortraitService`, and lifetime cap variable `PORTRAIT_TOTAL_LIMIT`. The private bucket must not acquire public custom/r2.dev access. Never recreate storage namespaces or reset a ledger to solve a quota/test problem.

`worker/portraits/service.mjs` provides status, session POST/DELETE, jobs POST, job status/image GET and explicit job deletion. Login uses high-entropy capability passes represented server-side as hashes. Sessions use hashed server state and `__Host-cc-portrait` with Secure, HttpOnly and SameSite=Strict. Mutations require the exact origin and `X-Cortex-Request: portrait-v1`. Grants have expiry and finite allowances; valid existing artwork can be reused at zero remaining generation allowance. The configured global cap is 100 total attempts and 25/day; actual account limits and remaining balances are runtime data, not promised by this handoff.

Job admission validates the visual spec, requires consent, atomically reserves account/global/daily quota, binds request ID to the spec fingerprint and enqueues before provider work. Same request/spec reuses the job; mismatched idempotency IDs fail. A running request with uncertain outcome is never automatically resubmitted. Recovery may promote an already stored image to ready. Deletion is a tombstone/recovery flow so queued/running work cannot recreate deleted artwork; device and downloaded PDF copies are outside cloud deletion. Review the whole service before modifying its state machine.

`worker/portraits/xai.mjs` pins `grok-imagine-image-2.0`, medium quality, 2K, 3:4, one image, base64 response. Current official pricing was researched in the earlier release; recheck provider docs before making new cost promises. It enforces approved fields, response/image bounds, a hash and moderation failures. Runtime fetch uses a non-following redirect mode; an earlier unsupported mode caused pre-provider failures. Do not restore that option. `xaiVisual.mjs` is shared with the UI so the confirmed and submitted visual brief match. Only enumerated visual preferences and approved symbolic motifs leave the browser.

## Client portrait storage
`portraitDevice.mjs` validates, decodes, bounds and re-encodes initially accepted artwork; device records use IndexedDB and a SHA-256 reference, not a remote tracking URL. Restore of an already accepted backup preserves its JPEG bytes. `storage.mjs` normalizes the nested hero record, visual choices and asset reference; the old separate hero storage key is migration compatibility, not the preferred save path. `portraitLibrary.mjs` selects matching directions/editions and provides progress labels. `XaiPortraitControls.jsx` handles explicit generation/use/delete actions, stale response suppression and acknowledgement before using artwork from another visual direction. That acknowledgement does not change questionnaire answers or the selected hero.

## Backup module
`backup/cryptoEnvelope.mjs`: fixed versioned `.cortex` envelope, 12 MB bound, PBKDF2-HMAC-SHA256 with 600000 iterations, 16-byte random salt, 12-byte IV and AES-256-GCM with authenticated header. `backup/profileBackup.mjs`: canonical save normalization, bounded JPEG/base64 content and hash validation; profile format `cortex-compass-profile-backup`, v1, portrait max 8 MB. `backup/backupActions.mjs`: prepare file, preview and open with explicit consent. `components/backup/ProfileBackup.jsx`: password handling, invalidating outdated downloads, read-only preview and consent UI. The legacy non-runtime `.draft` under docs is not the current UI. No backup function should upload questionnaire data or replace saved data merely on decrypt.

## Change coupling
Hero IDs are consumed by the scientific text, portrait compiler, server allowlist, saved preferences and visual fingerprints. Adding/renaming heroes is therefore not a frontend-only change. Introduce versioned aliases or migration rules; preserve old accepted artwork and never regenerate it because a scientific citation changed. New graph outputs must not bypass the allowlist or put sensitive context into an image prompt. Changes to required input must preserve old records without fabricating a response. Changes to report CSS require real PDF inspection, not only DOM tests.
